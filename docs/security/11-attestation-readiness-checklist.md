# 11. Чек-лист готовности к аттестации

## Назначение

Чек-лист используется перед подготовкой `Second Shelf` к итоговой аттестации в конкретной среде размещения.
Он помогает отделить то, что уже подтверждается кодом, от того, что должно быть доказано инфраструктурой и эксплуатацией.

## Статусы

- `Готово в коде` — подтверждается текущим приложением;
- `Нужно в инфраструктуре` — без этого аттестация не может считаться завершенной;
- `Открытый вопрос` — требует решения или доказательств.

## Чек-лист

| Пункт | Статус | Комментарий |
| --- | --- | --- |
| Классификация системы как `3-ИН` предварительно зафиксирована | Готово в коде / документации | Основание описано в `01-system-classification.md` |
| Зафиксирован перечень сервисов и зон владения данными | Готово в коде / документации | Описаны `auth-service`, `user-service`, `book-service`, `exchange-service`, `notification-service` |
| Подтвержден реестр ПДн | Готово в документации | Требует согласования владельцем процесса |
| JWT-аутентификация и refresh-ротация реализованы | Готово в коде | Требуется проверить безопасные секреты в среде |
| Пароли хранятся в виде хэша | Готово в коде | bcrypt в `user-service` |
| Внутренние API отделены и защищены отдельным токеном | Готово в коде | Требуется ротация и secret manager |
| Разграничение доступа по владельцу и участнику реализовано | Готово в коде | Требуются результаты негативного тестирования |
| Изолированные БД по сервисам реализованы | Готово в архитектуре | Требуются раздельные права доступа и network ACL |
| Outbox и DLQ реализованы | Готово в коде | Требуются алерты и регламент re-drive |
| Health checks доступны | Готово в коде | Требуется ограничить технические интерфейсы в production |
| TLS для внешнего и внутреннего трафика включен | Нужно в инфраструктуре | В приложении не реализуется |
| Firewall и сегментация сети настроены | Нужно в инфраструктуре | Особенно для БД, RabbitMQ и `/internal/**` |
| Централизованное логирование и хранение аудита настроены | Нужно в инфраструктуре | Логи должны быть защищены и доступны для расследования |
| Backup storage настроен и протестирован | Нужно в инфраструктуре | Требуется журнал тестов восстановления |
| IDS/IPS и DNS-логирование подключены | Нужно в инфраструктуре | Не относится к runtime-коду |
| EDR/антивирус развернут на хостах | Нужно в инфраструктуре | Не относится к runtime-коду |
| Синхронизация времени на всех узлах включена | Нужно в инфраструктуре | Важна для логов, сроков токенов и расследований |
| Secret manager используется для `JWT_SECRET`, `INTERNAL_TOKEN`, БД и RabbitMQ | Нужно в инфраструктуре | Default values из репозитория недопустимы |
| Swagger и Actuator ограничены для production | Открытый вопрос | В коде endpoints открыты без JWT |
| Seed admin credentials заменены или отключены | Открытый вопрос | Нужно проверить конкретную среду |
| Политика retention утверждена и исполняется | Открытый вопрос | В коде нет автоматической очистки данных |
| Назначены ответственные за реагирование на инциденты | Открытый вопрос | Требуется эксплуатационный регламент |
| Подтверждены процедуры восстановления после сбоя | Открытый вопрос | Нужны фактические тесты восстановления |

## Итог

`Second Shelf` имеет хороший прикладной baseline для подготовки к аттестации: JWT, refresh-токены,
хэширование паролей, внутренний токен, owner-based authorization, изолированные БД, outbox, DLQ и health checks.
Однако итоговая готовность к аттестации определяется конкретной средой развертывания и набором инфраструктурных мер,
поэтому этот чек-лист должен закрываться совместно приложением, DevOps-контуром и эксплуатационной документацией.
